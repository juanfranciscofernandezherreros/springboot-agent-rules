Fallos e incidencias

#IncidenciaCausaCorrección
1La primera lectura de archivos falló con un error del sandbox (apply deny-read ACLs).Limitación transitoria del helper de filesystem.Se solicitó autorización para una lectura no destructiva y se leyeron AGENTS.md, START_HERE.md y todos los documentos relevantes.
2Spotless 2.51.0 no existía en Maven Central.Versión inicial incorrecta.Se consultó el metadato oficial de Maven Central y se usó Spotless 3.10.2.
3La prueba MVC no compilaba: org.springframework.boot.test.mock.mockito.MockitoBean no existía.Cambio de paquete en Spring Boot 4 / Spring Framework 7.Se migró a org.springframework.test.context.bean.override.mockito.MockitoBean.
4La corrección anterior introdujo un BOM UTF-8 y Java informó illegal character: '\ufeff'.La escritura PowerShell usó una codificación con BOM.Se reescribió el archivo en UTF-8 sin BOM y Spotless volvió a pasar.
5El primer arranque Compose no pudo reservar el puerto 1433.El puerto ya estaba ocupado por otro proceso/contenedor local.Se usó el puerto de host 1434, manteniendo 1433 dentro de la red Compose.
6El siguiente arranque no pudo reservar el puerto 8080.El puerto ya estaba ocupado localmente.Se usó el puerto de host 8081; la aplicación sigue escuchando en 8080 dentro del contenedor.
7La API no encontraba la base de datos orders.Las comillas del comando de inicialización Compose se transformaron y la condición SQL quedó mal formada.Se sustituyó la condición por una expresión T-SQL idempotente sin comillas conflictivas y se recrearon contenedores sin eliminar el volumen.
8Hibernate indicó que faltaba la tabla orders.En Spring Boot 4, tener solo flyway-core y el módulo SQL Server no activaba la autoconfiguración requerida.Se añadió spring-boot-starter-flyway. Los logs confirmaron la validación de la migración V1 antes de validar Hibernate.
9El primer intento del script de persistencia se detenía tras el POST.El ejecutable bash resolvía a WSL, donde Docker no estaba integrado.Se ejecutó con Git Bash y se añadieron llamadas Compose compatibles con la conversión de rutas de MSYS.
10Durante el reinicio, algunas llamadas iniciales a health devolvieron respuesta vacía.La aplicación todavía estaba iniciando.El script tenía reintentos acotados; terminó cuando la API estuvo lista. El estado final fue saludable.

Preguntas de autorización realizadas

Las preguntas no fueron decisiones de producto. Fueron solicitudes obligatorias del entorno para ejecutar acciones locales con permisos elevados:

  • Leer las instrucciones y estándares del repositorio.
  • Consultar Maven y Docker instalados.
  • Descargar Maven Wrapper, dependencias y el plugin Spotless.
  • Construir, formatear y ejecutar pruebas.
  • Validar, construir y arrancar Docker Compose.
  • Inspeccionar logs y estado de contenedores para diagnosticar fallos.
  • Recrear contenedores sin borrar volúmenes.
  • Ejecutar las comprobaciones HTTP y SQL Server de persistencia.

Automatización de AGENTS.md

Las reglas de AGENTS.md se pueden convertir en un flujo automático: lectura de reglas, generación, validación estática, formato, pruebas, Compose, HTTP, SQL Server y prueba de persistencia. De hecho, el repositorio ya dispone del CLI agent-rules para orquestar buena parte de ello.

Límite práctico: la lectura de instrucciones, la generación y las comprobaciones pueden automatizarse; no así los diálogos de permiso impuestos por el sandbox, los puertos ocupados o dependencias externas como Docker, red y Maven Central. El flujo debe detectar estos casos, aplicar alternativas seguras predefinidas (por ejemplo, puertos configurables) o pedir autorización.

Para ejecutar la validación automatizada del proyecto generado: agent-rules verify generated/orders-api. En Windows, la parte de shell del script de persistencia debe ejecutarse mediante un Bash con acceso a Docker, como Git Bash configurado adecuadamente.
